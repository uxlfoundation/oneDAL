# Formal methods for oneDAL: a pilot on basic_statistics

This directory is a pilot. It answers one question: on real oneDAL code, what do
a model checker (TLA+) and a proof assistant (Lean 4) find, and what do they
cost? It covers a single code path, the GPU dense `basic_statistics` compute
(`cpp/oneapi/dal/algo/basic_statistics/backend/gpu/compute_kernel_dense_impl_dpc.cpp`),
plus the CPU (DAAL) `low_order_moments` merge that implements the same math.
Nothing here is built or run by the library build or CI.

## The idea

oneDAL code has two kinds of claims that tests check poorly:

1. **Protocol claims.** "The merge kernel never reads a block before the block
   kernel wrote it", "the host never frees a buffer a kernel still uses", "every
   rank issues the same collectives". Bugs here depend on timing and show up rarely.
   A test run sees one interleaving. A model checker sees all of them on a small
   configuration.
2. **Math claims.** "Merging partial results of any partition, in any order, gives
   the statistics of the whole data set." Tests check a few partitions. A proof
   covers all of them, but only in exact arithmetic.

Each claim is written down as a small model next to the code, the model is
checked by a tool, and the model is tied to the code by a mapping table (below).
The model is not the code: a model that passes says the *design* is right. It
does not say the C++ does what the model says.

Floating point is a third question that neither tool answers. Exact-arithmetic
proofs cannot see rounding: the CPU defect this pilot found is a formula that is
correct over the reals and wrong in double. The numeric harness checks that part.

| Tool | Answers | Does not answer | Cost to run |
| --- | --- | --- | --- |
| TLA+ / TLC | Can any interleaving of these steps break this invariant, for sizes up to N? | Anything above N; whether the C++ matches the model | seconds |
| Lean 4 + Mathlib | Is this formula right for every input, over the reals? | Rounding; whether the C++ matches the formula | 17 s build, 5 GB cache |
| Numeric harness | How far is the real implementation from an exact reference on hard data? | Inputs not tried; no bound is proved | seconds to minutes |

## Layout

```text
dev/formal/
  tla/MergeBlocks.tla      model of compute_by_blocks -> merge_blocks (147 lines)
  tla/run.sh               writes a TLC config and runs one check
  lean/OnedalStats/Moments.lean  definitions and theorems for count/mean/M2 merge
  lean/AxiomCheck.lean     prints the axioms every theorem depends on
  lean/lakefile.toml, lean-toolchain, lake-manifest.json  pinned Lean and Mathlib
  numeric/replica.cpp      host copy of the GPU kernel arithmetic
  numeric/experiment.py    runs replica and daal4py against exact rationals
  numeric/summarize.py, cancellation.py  tables from the run
```

The models are the deliverable: `MergeBlocks.tla` and `Moments.lean`, about 430
lines together. Everything a run produces (TLC configs and traces, `results.json`,
tables, `axioms.txt`) is ignored by git and regenerated by the commands below.

## How to run

TLA+ needs Java 11+ and `tla2tools.jar`
(https://github.com/tlaplus/tlaplus/releases):

```sh
export TLA2TOOLS=/path/to/tla2tools.jar
dev/formal/tla/run.sh base_L4_B4 4 4 '{}'            # no mutation: must pass
dev/formal/tla/run.sh mut_nowait 4 4 '{"nowait"}'    # mutation: must fail
```

`run.sh NAME L B MUT` checks one work-group of `L` work-items merging `B` blocks.
`MUT` is a set of mutations, from `"nodep"`, `"nowait"` and `"nobarrier"`. The exit
status is TLC's: 0 when every property holds, non-zero with a trace in
`tla/out/NAME.log` when one fails.

Lean needs `elan` (https://github.com/leanprover/elan). The toolchain is pinned:

```sh
cd dev/formal/lean
lake exe cache get        # Mathlib binaries, about 5 GB, once
lake build                # fails on any unproved goal
lake env lean AxiomCheck.lean
```

The last command must print only `propext`, `Classical.choice` and `Quot.sound`
for every theorem. Anything else (`sorryAx`, a custom axiom) means a gap in a proof.

Numeric harness (Python with `numpy` and `daal==2025.10.0`):

```sh
cd dev/formal/numeric
g++ -O2 -ffp-contract=off -o replica replica.cpp
g++ -O2 -ffp-contract=fast -march=native -o replica_fma replica.cpp
python experiment.py .            # writes results.json and summary.md
python summarize.py results.json   # splits supported and unsupported configurations
python cancellation.py > cancellation.md
```

## What the pilot covers

### A. TLA+: `compute_by_blocks` -> `merge_blocks`

| Model step | Code |
| --- | --- |
| `SubmitK1`, `K1Write` | `compute_by_blocks`: `q_.submit` of `block_processor_kernel`, writes `ndbuf` |
| `SubmitK2` | `merge_blocks`: `q_.submit` with `cgh.depends_on(deps)` |
| `Load` | `merge_blocks_kernel` first loop `for (i = id; i < block_count; i += local_size)` |
| `Barrier` | `sycl::group_barrier` at the top of each tree round |
| `Reduce` | `if (stride > id)` merge the partner slot; `if (0 < id)` store own slot |
| `Finish` | `if (0 == id)` write the group result |
| `Wait` | `last_event.wait_and_throw()` at the end of `merge_blocks` |
| `Free` | `ndbuf` (a local of `compute_by_blocks`) destroyed on return; `usm_deleter` calls `sycl::free`, which does not wait |

The runtime rules come from SYCL 2020: `depends_on` delays the command group
until the event completes, `wait_and_throw` returns after the command completes,
`group_barrier` orders work-group local memory, and freeing USM that a running
command still uses is undefined (the model treats free as not waiting).

Properties: no use after free, no read of a block before it is written, no stale
local-memory read in the tree, every block merged exactly once, result read only
after the merge kernel finishes, and termination.

| Check | Result |
| --- | --- |
| No mutation, L <= 8, B <= 16 (6 configurations) | all properties hold; largest is 132,705 states in 5 s |
| Drop `depends_on` | counterexample: merge reads an unwritten block |
| Drop `wait_and_throw` | counterexample: host frees `ndbuf` while merge is still queued (10 steps) |
| Drop `group_barrier` | counterexample: stale local-memory read |
| `B < L` and `B` not a power of two (L=4, B=3) | counterexample: block 2 is never merged |

The last row is a hidden precondition, not a live bug: `get_row_block_count`
returns only 1, 8, 16, 32, 64 or 128, and sub-group sizes are powers of two on
current devices, so the case does not occur today. An assertion in `merge_blocks`
would make the precondition explicit.

### B. Lean 4: count/mean/M2 merge

| Theorem | Statement (over the reals) | Code |
| --- | --- | --- |
| `merge_ofList` | merging two blocks gives the count, mean and M2 of the concatenated data | `merge_blocks_kernel` merge step |
| `merge_comm`, `merge_assoc` | merge order and tree shape do not change the result | tree reduction, rank order |
| `merge_empty_left/right` | an empty block `(0, 0, 0)` is neutral | contract for empty partial results |
| `merge_valid` | merge keeps `n >= 0`, and `n = 0` keeps mean and M2 at 0 | |
| `kwayM2_correct` | `sum_r (M2_r + n_r * (mean - mean_r)^2)` is the M2 of all data | distributed `finalize` |
| `mergeBad_wrong` | dropping `/N` from the merge gives 20 instead of 8 on `[0]`, `[2, 4]` | negative check |
| `daal_term_eq` | DAAL's `m1*m1 + m2*m2 - 2*m1*m2` equals `(m2 - m1)^2` | DAAL CPU merge |

In Lean `x / 0 = 0`, so an empty block is neutral in the model. In IEEE arithmetic
the kernel computes `0 / 0 = NaN` for an empty block, so empty blocks must stay
outside the kernel's contract, and today they do.

### C. Numeric harness and the defect it found

`daal_term_eq` says DAAL's expanded term is exact over the reals. In double, with
means near 1e8, the squares are near 1e16 and their difference is rounding noise.
On `1e8 + N(0, 1e-3)` data, released daal4py 2025.10.0 streamed in 3 or more
chunks returns the variance with up to 1.9e5 relative error, sometimes negative.
The host copy of the GPU arithmetic stays within 3e-6 on the same data. The fix
and a regression test are in uxlfoundation/oneDAL#4014.

## Proved, checked, tested, assumed

| Claim | Status |
| --- | --- |
| Merge formulas give the statistics of the union, in any order; empty is neutral | proved in Lean, exact arithmetic only |
| `merge_blocks` dependency, lifetime and barrier protocol | model-checked for L <= 8, B <= 16; never run on a GPU |
| Removing any of the three synchronisation points breaks it | model-checked (mutations of the model, not of the kernel) |
| DAAL CPU online merge loses the variance at large offsets | tested with daal4py; fixed in #4014 with a red/green test |
| GPU kernel arithmetic is accurate at offset 1e8 | host copy only, not the device |
| Sub-group sizes are powers of two; `sycl::free` does not wait | assumed |

## Scope: where this could go

The pilot suggests one rule for picking targets: model a thing only when a bug
in it is expensive and tests cannot find it. That gives a short list, not
library-wide coverage.

| Area | Tool | Candidates | Why |
| --- | --- | --- | --- |
| Merge and finalize math | Lean | covariance and cross-product merge, linear regression `X^T X` / `X^T y` merge, PCA online, low_order_moments GPU primitives (`backend/primitives/stat`) | one theorem file per formula; the same few lemmas repeat |
| Same formulas in floating point | numeric harness | every online and distributed merge, run against an exact reference on large-offset and skewed data | found the only real defect in the pilot; known open sites: `pca_dense_svd_online_impl.i:148`, `covariance_impl.i:850` |
| SPMD collectives | TLA+ | `finalize` and other distributed paths: every rank issues the same collective sequence, ranks with zero rows | deadlocks and wrong reductions appear only on clusters |
| Kernel synchronisation and USM lifetime | TLA+ | kernels that free temporaries right after `submit`, multi-kernel event chains | same model shape as `MergeBlocks.tla` |
| Online `partial_compute` / `finalize` state | TLA+ or plain tests | result-option masks, the init step, empty partial results | the mask bug in `test/online.cpp` was this class |

Out of scope: whole-algorithm proofs (k-means convergence, SVM optimality),
proofs about generated or vectorised kernels, and anything that needs a model of
IEEE rounding. The cost grows faster than the benefit there.

## Support cost

| Item | One-off | Ongoing |
| --- | --- | --- |
| One TLA+ protocol model | 1-3 days | update the mapping when the mapped functions change; about 1 hour per such change |
| One Lean theorem file | 0.5-2 days | Mathlib upgrade breaks tactics about once per pinned bump; the pin avoids forced upgrades |
| Numeric harness per algorithm | 0.5 day | none unless the API changes |
| CI, if adopted | one path-filtered job: TLC in seconds, Lean 3-5 min with a cached Mathlib | the cache is about 5 GB |

The main long-term risk is drift: a model that still passes after the code
changed proves nothing. A path filter that flags a PR changing a mapped file
without touching its model would keep the two together.
